# 구현 계획을 Jira에 등록

설계 문서의 `## 구현 계획` 섹션을 읽어 Jira에 Task와 Subtask를 만들고, Phase 라벨과 의존성 링크를 붙입니다.

**전제**: `decompose-design`으로 분해가 끝나고 사용자 승인까지 받아 설계 문서에 반영된 상태여야 합니다. 그 섹션이 없으면 여기서 멈추고 `decompose-design`을 먼저 쓰라고 안내합니다.

## 계층 매핑

| 설계 문서 | Jira 이슈 타입 | 계층 |
|---|---|---|
| Task (설계 문서 1개) | **에픽** | 1 |
| Subtask (= PR 1개) | **작업** (또는 스토리) | 0 |

Jira의 `Subtask`(계층 -1) 타입을 쓰지 않습니다. **보드에 카드로 표시되지 않아 PR 단위 진행 상태를 추적할 수 없습니다.** 용어가 어긋나지만 중요한 건 이름이 아니라 1 PR = 1 카드입니다.

**입력**: 설계 문서 경로.

---

## 0단계. 사전 확인

**이미 등록됐는지 먼저 봅니다.** 설계 문서의 구현 계획 표에 이슈 키(`KAN-12` 같은)가 이미 적혀 있으면 중복 생성하지 않습니다. 사용자에게 알리고, 추가된 Subtask만 만들지 아니면 그만둘지 묻습니다.

그다음 아래를 확인합니다.

1. `getAccessibleAtlassianResources`로 cloudId를 얻습니다. **하드코딩하지 않습니다.**
2. `getVisibleJiraProjects`로 대상 프로젝트를 확인합니다. 여러 개면 사용자에게 묻습니다.
3. `getJiraProjectIssueTypesMetadata`로 이슈 타입 이름을 확인합니다. 사이트 언어에 따라 `작업`/`Task`, `스토리`/`Story`로 다르므로 **이름을 가정하지 않고 조회한 값을 씁니다.**

---

## 1단계. 에픽 생성

구현 계획의 Task마다 `createJiraIssue`로 에픽을 만듭니다. 설계 문서 하나는 보통 Task 1개이므로 에픽도 1개입니다.

- `issueTypeName`: 0단계에서 확인한 hierarchyLevel 1 타입 (보통 `에픽`)
- `summary`: 설계 문서를 총칭하는 주제
- `description`: 무엇을 만드는지 한두 문장 + 설계 문서 경로

---

## 2단계. 작업 생성

에픽 아래에 작업을 만듭니다. **Phase 순서대로, 같은 Phase 안에서는 권장 순서대로 만듭니다.** 보드에서 생성 순서가 곧 작업 순서로 보이게 하기 위해서입니다.

- `issueTypeName`: hierarchyLevel 0 타입 (보통 `작업`)
- `parent`: 에픽의 이슈 키
- `summary`: 설계 문서의 Subtask 제목 (`<타입> <한글 설명>` 형식 그대로)
- `additional_fields`: `{"labels": ["phase-1"]}` 형태로 Phase 라벨
- `description`: 변경 범위, 리뷰 포인트, 예상 규모

필드 설정이 실패하면 `createJiraIssue`가 400 에러를 반환합니다. **직접 우회하지 말고 사용자에게 보고합니다.** Phase를 제목에 끼워 넣는 식의 임시방편은 제목 규칙을 깨뜨립니다.

---

## 3단계. 의존성 링크

설계 문서의 `의존` 컬럼대로 `createIssueLink`를 겁니다.

- `type`: `Blocks`
- `inwardIssue`: **먼저 끝나야 하는 쪽** (선행 작업)
- `outwardIssue`: **기다리는 쪽** (후행 작업)

방향을 반대로 걸면 보드에서 순서가 거꾸로 읽히므로 주의합니다. `A is blocked by B`는 `inwardIssue: B, outwardIssue: A`입니다.

Phase 라벨과 Blocks 링크는 같은 정보를 다르게 표현한 것입니다. 라벨은 보드 필터용, 링크는 개별 이슈에서 선후 관계를 보기 위한 것이라 둘 다 겁니다.

---

## 4단계. 설계 문서에 이슈 키 반영

생성된 이슈 키를 설계 문서의 구현 계획 표에 다시 써넣습니다. **이 단계를 빠뜨리면 문서와 Jira를 연결할 방법이 없어집니다.**

- Subtask 상세 표에 `이슈 키` 컬럼을 추가하거나 채웁니다
- Phase별 계획의 각 항목 앞에도 이슈 키를 붙입니다

---

## 5단계. 보고

만든 것을 요약해 보고합니다.

- 에픽과 작업 개수, Phase별 분포
- 각 이슈 키와 제목
- 실패한 항목이 있으면 무엇이 왜 실패했는지

브랜치를 팔 때 쓸 이름도 함께 제시합니다. `rules/commit.md`의 브랜치 규칙에 이슈 키를 넣은 형태입니다.

```
feat/TEST-12-review-comment-formatter
```

PR 제목도 함께 제시합니다.

```
TEST-12 feat 리뷰 결과 코멘트 포맷터 추가
```

---

## 하지 않는 것

- **브랜치 생성, 코드 작성** — 이 스킬은 티켓 등록까지입니다
- **이슈 상태 전이** — 진행중/완료 전환은 구현 단계의 일이고 이 스킬의 범위가 아닙니다
- **설계 내용 수정** — 구현 계획 표에 이슈 키를 채우는 것 외에 설계 문서를 고치지 않습니다
- **이미 만든 이슈 재생성** — 0단계에서 확인하고 멈춥니다

| 합리화 | 반박 |
|--------|------|
| "티켓 만들었으니 첫 브랜치까지 파두자" | 등록과 구현은 다른 결정이다. 사용자가 언제 시작할지 고른다. |
| "라벨이 안 붙으니 제목에 Phase를 넣자" | 제목 규칙을 깨는 우회다. 보고하고 사용자가 정한다. |
| "Jira에 Subtask 타입이 있으니 그걸 쓰자" | Subtask는 보드에 카드로 안 뜬다. 계층 0을 쓴다. |
| "설계 문서에 키 채우는 건 나중에 해도 된다" | 나중은 오지 않는다. 키가 없으면 문서와 보드가 따로 논다. |
