# 설계 문서 분해

설계 문서를 구현 단위로 분해하고, 의존성을 분석해 Phase와 순서를 정한 뒤, 사용자 확인을 받아 설계 문서에 반영합니다.

설계를 문서로 꺼내면 어떻게 분해할지 방향이 보입니다. 사람이 머릿속으로만 하던 분해와 순서 결정을 문서에 명시적으로 남기면, 사람은 맞는지 판단만 하면 됩니다.

## 계층

| 층 | 의미 | 대응 |
|----|------|------|
| **Task** | 설계 문서의 기능 묶음 | JIRA Task |
| **Subtask** | 독립적으로 구현하고 리뷰할 수 있는 단위 | JIRA Subtask = PR 1개 |
| **Phase** | 동시에 진행할 수 있는 Subtask 묶음 | 구현 순서의 단계 |

Task와 Subtask는 기능을 나눈 결과이고, Phase는 의존성에서 자동으로 떨어집니다. Phase는 Task를 가로지릅니다.

입력: 설계 문서 경로. 없으면 사용자에게 요청하고 여기서 멈춥니다.

---

## 1단계. 분해 (Task → Subtask)

설계 문서의 기능 묶음을 Task로 잡고, 각 Task를 Subtask로 나눕니다. 설계가 기능 하나뿐이면 Task 1개에 Subtask 여러 개가 됩니다.

**Subtask는 기능 단위입니다.** 하나의 Subtask는 사용자나 운영자 관점에서 의미 있는 기능 하나이고, 그 기능에 필요한 엔티티, 리포지토리, 서비스, 컨트롤러가 한 단위 안에 같이 들어갑니다.

**계층으로 나누지 않습니다.** "엔티티만 1개, 리포지토리만 1개"로 나누면 리뷰어가 그 변경이 왜 필요한지 판단할 근거가 PR 안에 없습니다. 같은 이유로 기능을 가로질러 자르지 않습니다. 줄 수를 줄이려고 웹훅 수신부만, 조회 로직만 떼면 크기는 줄어도 리뷰어가 맥락을 잃어서 더 나빠집니다.

### 기반 코드 분리 (유일한 예외)

Subtask가 너무 커서 한 번에 읽기 어려울 때, **아래를 모두 만족하는 기반 코드**만 앞선 Subtask로 뗍니다.

- 2개 이상의 Subtask가 실제로 공유한다
- 그 자체로 단위 테스트를 붙일 수 있다

두 번째가 중요합니다. 테스트가 안 붙는 코드를 떼면 검증 불가능한 죽은 코드 PR이 됩니다. 그때는 크더라도 원래 Subtask에 포함시키고, PR 내부를 논리적 커밋으로 나눌 계획을 적습니다.

### 쪼개지 않고 합치는 경우

- 쪼개면 컴파일되지 않거나 테스트를 붙일 수 없다
- 쪼갠 둘이 항상 같이 배포되어야만 의미가 있다
- 변경 파일이 1~2개이고 diff가 수십 줄 수준이다
- 둘을 따로 릴리스 노트에 쓸 일이 없다 (같은 기능이다)
- B가 A를 넓히거나 보강할 뿐 새로운 관심사를 들여오지 않는다

**크기는 합치는 사유가 아닙니다.** 작다는 이유로 합치지 않고 주제가 같을 때만 합칩니다. 합칠지 애매하면 합치지 말고 두 안을 적어 사용자가 고르게 합니다.

### 제목으로 검산

제목에 `및`이나 쉼표 나열이 필요하면 **나눌 후보**입니다. 나열은 신호일 뿐이고, 실제로 나눌지는 이것으로 판정합니다.

> 나눈 각각이 **그것만 배포해도 쓸모가 있는가?**

- 둘 다 쓸모가 있다 → 나눕니다. 제목도 각각 구체적으로 씁니다
- 한쪽이 반쪽이 된다 → 합치고, 둘을 아우르는 상위어 제목을 씁니다

상위어 제목은 **합친 경우에만** 허용합니다. 나누지 않으려고 제목을 추상화해서 넘기는 것과는 다릅니다. 큰 덩어리를 "OO 기능 추가" 한 줄로 뭉개는 것은 여전히 통과가 아닙니다.

| 예시 | 나열 | 독립 배포 쓸모 | 결론 |
|---|:---:|---|---|
| 태그 추가 / 태그 제거 | O | 추가만 있으면 뗄 수 없다 | 합침 → `태그 관리` |
| 메모 수정 / 메모 삭제 | O | 수정만 배포해도 쓸 수 있다 | 나눔 |
| 메모 작성 / 단건 조회 | O | 작성만 있으면 저장한 걸 볼 수 없다 | 합침 |
| 메모 작성 / 태그 검색 | O | 각각 쓸모가 있다 | 나눔 |

판정 기준이 "쪼개지 않고 합치는 경우"의 **항상 같이 배포되어야만 의미가 있다**와 같습니다. 두 규칙이 같은 것을 보므로 서로 충돌하지 않습니다.

## 2단계. 의존성

각 Subtask에 대해 "이것보다 먼저 머지되어야 하는 Subtask"를 적습니다.

**거짓 의존성을 제거합니다.** 순서가 자연스러워 보인다는 이유는 의존성이 아닙니다. 먼저 머지되지 않으면 실제로 컴파일이나 테스트가 깨질 때만 의존입니다. 거짓 의존성을 남기면 병렬 진행이 가능한 작업이 불필요하게 직렬화되고 Phase가 쓸데없이 늘어납니다.

방향 판정 힌트는 데이터 계층 → 도메인 → API입니다. 분할 기준이 아니라 방향만 보는 용도입니다.

---

## 3단계. Phase 편성과 순서

의존성 그래프를 위상 정렬해 Phase를 만듭니다.

- **Phase 1**: 선행 의존이 없는 Subtask 전부
- **Phase N**: 선행 의존이 모두 Phase N-1 이하에 있는 Subtask 전부

같은 Phase 안의 Subtask는 서로 의존하지 않으므로 **병렬 진행이 가능합니다.**

그 안에서도 **권장 순서를 매깁니다.** 혼자 구현하면 병렬이 무의미하므로 순서가 필요합니다. 기준은 뒤 Phase가 많이 기다리는 것부터, 불확실성이 큰 것부터입니다.

순환 의존이 나오면 Phase를 만들지 말고 1단계로 돌아갑니다. 서로를 필요로 하는 둘은 같은 Subtask여야 합니다.

## 4단계. 제시

아래 형식으로 사용자에게 제시하고 **응답을 기다립니다.**

### Phase별 구현 계획

```
Phase 1 — 병렬 가능
  1. [ID] 제목 (Task)
  2. [ID] 제목 (Task)
Phase 2
  1. [ID] 제목 (Task)
```

### Subtask 상세

| ID | Task | 제목 | 변경 범위 | 의존 | Phase | 순서 | 예상 규모 | 리뷰 포인트 |
|----|------|------|-----------|------|-------|------|-----------|-------------|

- **제목**: `<타입> <한글 설명>`. 타입과 브랜치 네이밍은 `~/.claude/rules/commit.md`를 따릅니다.
- **예상 규모**: 참고용입니다. 설계 문서에는 줄 수가 없으므로 같은 저장소에서 성격이 비슷한 기존 기능에 견주어 추정하고, **무엇에 견주었는지 함께 적습니다.**

### 판단이 필요한 지점

- 합칠지 나눌지 애매했던 곳: 두 안과 트레이드오프 한 줄
- 한 번에 읽기 버거운 Subtask: 왜 더 나눌 수 없는지와 PR 내부 커밋 분할 계획

마지막에 이렇게 묻습니다.

> "분해안을 검토해주세요. 수정할 부분을 알려주시면 반영하고, 이대로 괜찮으면 설계 문서에 넣겠습니다."

## 5단계. 설계 문서에 반영

**사용자가 승인한 뒤에만** 설계 문서를 수정합니다. 수정 없이 승인하면 제시한 내용 그대로, 수정 요청이 있으면 반영한 뒤 넣습니다.

- 설계 문서 끝에 `## 구현 계획` 섹션을 추가합니다. 이미 있으면 그 섹션만 교체합니다.
- 설계 내용 자체는 건드리지 않습니다. 분해 결과만 덧붙입니다.
- 4단계에서 제시한 Phase별 계획과 Subtask 상세 표를 그대로 넣습니다.

반영하면 이 스킬의 일은 끝입니다. 브랜치 생성과 코드 작성은 범위가 아닙니다.

Jira를 쓰는 작업이면 마지막에 이어갈지 물어봅니다. 사용자가 원하면 `create-jira-subtasks` 스킬로 넘깁니다.

> "설계 문서에 반영했습니다. 이어서 Jira에 Task와 Subtask를 등록할까요?"

## 승인 전에 하지 않는 것

| 합리화 | 반박 |
|--------|------|
| "분해가 명확해서 바로 문서에 넣자" | 명확해 보이는 분해일수록 검토 비용이 싸다. 물어본다. |
| "문서에 먼저 쓰고 확인받자" | 문서에 쓰는 순간 분해안이 기정사실이 된다. 먼저 확인받는다. |
| "사용자가 전체 자동화를 원했다" | 자동화 대상은 반영 이후 단계다. 분해안 자체는 승인 대상이다. |
| "단위가 너무 작으니 합치자" | 크기는 합치는 사유가 아니다. 주제가 같을 때만 합친다. |
| "승인받았으니 티켓까지 만들자" | 승인 범위는 문서 반영까지다. 거기서 끝낸다. |

분해와 순서 결정은 설계의 연장이고 판단이 개입하는 지점입니다. 확인 없이 문서까지 고치면 형식적으로 훑고 지나가는 지점을 한 곳 더 만드는 셈이 됩니다.
