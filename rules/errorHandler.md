# 예외 처리 컨벤션

## 기본 구조

- 프로젝트의 커스텀 예외는 하나의 ...Exception(RuntimeException)을 기준으로 관리한다.
- ErrorCode enum에서 에러 코드, 메시지, HTTP 상태를 함께 관리한다.
- @ControllerAdvice를 사용하여 전역에서 예외를 처리한다.
- 에러 응답은 공통 DTO(예: ErrorResponse)를 사용하며 일관된 형식을 유지한다.

---

## 예외 처리 원칙

- 데이터 조회 실패는 orElseThrow()를 우선 사용한다.
- 비즈니스 규칙 위반은 조건 검증 후 커스텀 예외를 발생시킨다.
- 체크 예외는 필요한 경우 의미 있는 커스텀 예외로 변환하여 전파한다.
- 검증 로직이 복잡해지면 별도의 private 메서드로 분리하여 가독성을 높인다.
- 예외를 단순히 무시하거나 광범위하게 catch하지 않는다.

---

## 계층별 책임

### Controller

- 요청 검증, 인증 정보 확인 등 최소한의 역할만 수행한다.
- 비즈니스 로직은 Service에 위임한다.

### Service

- 비즈니스 규칙을 검증한다.
- 필요한 경우 커스텀 예외를 발생시킨다.

### Repository

- 데이터 접근만 담당한다.
- 비즈니스 예외를 직접 발생시키지 않는다.

### Global Exception Handler (@ControllerAdvice)

- 커스텀 예외를 공통 에러 응답으로 변환한다.
- 예상하지 못한 예외도 일관된 형식으로 처리한다.

---

## HTTP 상태 코드 사용 기준

| 상황 | HTTP Status |
|------|-------------|
| 잘못된 요청 또는 입력 | 400 Bad Request |
| 인증 실패 | 401 Unauthorized |
| 권한 부족 | 403 Forbidden |
| 데이터 없음 | 404 Not Found |
| 중복 데이터 | 409 Conflict |
| 비즈니스 규칙 위반 | 상황에 맞는 상태 코드 사용 |
| 서버 내부 오류 | 500 Internal Server Error |

---

## ErrorCode 작성 규칙

- 기능 또는 도메인별로 그룹화한다.
- 이름은 대문자 스네이크 케이스를 사용한다.
- 에러 메시지는 사용자 관점에서 이해하기 쉬운 한글로 작성한다.
- 하나의 ErrorCode는 하나의 의미만 갖도록 정의한다.
- 동일한 의미의 에러 코드를 중복 생성하지 않는다.
