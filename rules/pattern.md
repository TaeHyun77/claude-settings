# 코딩 패턴 컨벤션

## DTO

### Response DTO

- 엔티티를 외부에 직접 반환하지 않고 Response DTO를 사용한다.
- 엔티티와 DTO의 변환은 정적 팩토리 메서드(예: from())를 우선 사용한다.
- DTO는 불변 객체를 지향하며, 필요한 생성 방식을 일관되게 유지한다.

### Request DTO

- 요청 데이터는 Request DTO로 전달받는다.
- DTO에서 엔티티 생성이 필요한 경우 toEntity() 메서드를 사용한다.
- 입력 검증은 Bean Validation(@Valid)을 우선 활용한다.

---

## 엔티티

- @Setter는 지양하고 의미 있는 비즈니스 메서드로 상태를 변경한다.
- 생성자는 객체의 불변식을 보장하도록 설계한다.
- 공통 속성(예: 생성일시, 수정일시)은 공통 부모 클래스로 관리한다.
- 연관 관계는 기본적으로 지연 로딩(LAZY)을 사용하고, 즉시 로딩(EAGER)은 필요한 경우에만 사용한다.
- 연관 관계의 전이(cascade)와 orphanRemoval은 필요한 경우에만 명시적으로 사용한다.
- Builder는 객체 생성에 필요한 값만 포함하고, 식별자나 내부 관리 필드는 제외한다.

---

## Repository

- 단순 조회는 프레임워크가 제공하는 기본 기능을 우선 사용한다.
- 복잡한 조회는 별도의 Repository 구현 또는 Query 객체로 분리한다.
- N+1 문제가 발생하는 경우 Fetch Join, Entity Graph, Batch Fetch 등 적절한 전략을 사용한다.

---

## Controller

- 요청과 응답만 담당하고 비즈니스 로직은 Service에 위임한다.
- 성공 응답은 일관된 방식으로 반환한다.
- 본문이 없는 응답은 204 No Content를 사용한다.
- 예외 처리는 @ControllerAdvice에 위임하며 Controller에서 try-catch를 남용하지 않는다.

---

## Service

- 비즈니스 로직을 담당한다.
- 트랜잭션의 경계는 Service 계층에서 관리한다.
- 조회 전용 메서드는 필요한 경우 readOnly = true를 사용한다.

---

## 의존성 주입

- 생성자 주입을 기본으로 사용한다.
- 생성자는 Lombok의 @RequiredArgsConstructor 또는 명시적인 생성자를 사용한다.
- 필드 주입과 Setter 주입은 특별한 이유가 없는 한 사용하지 않는다.

---

## 네이밍

- 패키지는 기술이 아닌 도메인 중심으로 구성한다.
- 클래스명은 역할이 드러나도록 작성한다.
- DTO는 프로젝트에서 정한 규칙(예: Request, Response 또는 ReqDto, ResDto)을 일관되게 사용한다.
- 변환 메서드는 from(), toEntity() 등 의미가 명확한 이름을 사용한다.

---

## 공통 원칙

- 중복보다 일관성을 우선한다.
- 재사용 근거가 생길 때 추상화한다.
- 구현은 가능한 한 단순하게 유지한다.
- 코드 스타일과 설계는 프로젝트 전반에서 일관성을 유지한다.
